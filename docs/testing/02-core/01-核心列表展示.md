## [P1] 验证启用 loopback token 认证的新核心可完成 Desktop 握手
[测试类型] 功能 / 安全
[前置条件] 活动核心启动后输出 `dsh web: http://127.0.0.1:<port>/?token=<token>`，匿名访问 `/` 与插件 bundle 返回 401。
[测试步骤] 1. 由 Desktop 启动核心。2. 等待核心输出认证 URL。3. 检查 Desktop 健康状态与 iframe。4. 匿名请求 loopback API。5. 点击「在浏览器中打开」。6. 检查服务日志与运行日志。7. 停止监听端口但暂不结束 Node 进程，再执行健康检查。
[预期结果] 1. Desktop 捕获一次性 URL 后，通过真实 HTTP 请求确认端口仍可达，并进入 ready，不会永久停在「Waiting for Harness」。2. 一次性 `127.0.0.1` HTTP relay 只向独立的原生 Harness child WebView 返回 303；该 WebView 以字面 IPv4 顶层导航完成官方 token 交换并跳转无 token 的核心地址，避免 Tauri 壳与 iframe 的跨站 cookie 限制，也不会落到同端口的 `::1` 竞争监听器。token 不跨 IPC/JS，实际受保护 API 请求返回 200 后才进入 ready。3. 匿名 loopback API 仍返回 401，Desktop 不修改或绕过核心认证实现。4. 系统浏览器由 Rust 原生打开保留的认证 URL并完成自己的 cookie 交换，token 不经过前端。5. 交换、relay 或受保护 API 探测失败时保留同一 generation/PID 的交付权，重试可继续；旧 generation/PID 不能领取。6. 历史 marker 污染的托管核心必须经可信摘要下载原子替换；本地/linked 核心则拒绝启动并提示重装或重建。7. fresh 启动时 child WebView 先隐藏再导航，认证完成后首次即显示内容；全屏弹窗出现时 child 隐藏，帮助下拉、popover 或 toast 出现时只裁剪重叠边缘，关闭后恢复并同步完整内容区尺寸。8. 日志中的 token 被替换为 `<redacted>`，网络或浏览器打开错误也不含 URL/token。9. 端口停止监听后健康检查失败，不会仅凭缓存状态误报健康。10. 不输出认证 URL 的旧核心仍按插件 bundle 探测流程正常启动。
